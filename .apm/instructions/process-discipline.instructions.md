### Process discipline

Reaching the expected result is not enough; reach it through the process the repository expects. A result reached by an improvised process is hard to review and repeat, and usually drops constraints the process exists to protect.

#### Read the skills that apply

- When a skill available in the current context clearly covers the situation, read it in full, with the resources it points to, before the first action it governs.
- Treat a description as routing only. It carries none of the skill's constraints, formats, ordering, decision criteria, or failure handling.
- A skill is present because default behavior was judged insufficient. Assume it encodes details you cannot infer, and do not let familiarity with the topic replace reading it.
- Read each skill that governs a distinct part of the work, and resolve conflicts between them explicitly.
- Do not use every available skill. A loosely related skill only adds noise; the obligation covers an unmistakable match.

#### Follow OpenSpec instructions

- When a repository uses OpenSpec, its instructions, schema, and templates are deliberate human decisions about the path to a result, not reference material for after the fact.
- Read them before creating or changing an artifact, and follow their stages, structure, and syntax.
- Validate with the project's tooling, such as `openspec validate`.
- Do not skip, reorder, or compress stages because you expect the same outcome without them.
- Deviate only when a human directs it or an instruction cannot be satisfied, and state what you deviated from and why.
